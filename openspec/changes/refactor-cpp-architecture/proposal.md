# C++架构深度重构提案

## Why

当前C++代码库存在以下核心问题：

1. **架构问题**：
   - `tool.cpp` 3543行代码过度集中，职责不清
   - 缺乏模块化设计，代码难以维护和扩展
   - 全局变量泛滥（`g_extractedDomain`、`g_appName`等）
   - 缺少清晰的分层架构

2. **代码质量问题**：
   - 裸指针使用普遍，内存管理风险高
   - 缺乏统一的错误处理机制
   - 命名规范不一致（混合使用camelCase和snake_case）
   - 注释不完整，缺少文档

3. **性能瓶颈**：
   - 大量字符串拷贝操作
   - 加密解密未优化
   - Hook操作缺少性能监控
   - 缺少线程池和异步处理机制

4. **可维护性**：
   - 单一职责原则违反
   - 代码复用性差
   - 日志系统分散
   - 配置硬编码

通过深度重构，建立现代化C++架构，提升代码质量、性能和可维护性，为项目长期发展奠定基础。

## What Changes

### 阶段一：架构基础重构（核心层）
- 建立分层架构体系（Core、Service、Utils、JNI四层）
- 模块化拆分：网络模块、加密模块、Hook模块、Lua模块、存储模块
- 统一命名规范和代码风格
- 引入智能指针和RAII模式
- 建立统一日志系统

### 阶段二：服务层重构
- 实现依赖注入容器
- HTTP客户端服务化
- 加密服务优化（性能提升）
- Hook管理器重构
- 线程池实现

### 阶段三：工具层优化
- 字符串工具类（减少拷贝）
- 时间工具类
- 文件工具类
- 内存管理工具
- 性能监控工具

### 阶段四：安全与性能
- 内存清理机制
- 字符串混淆优化
- 加密性能优化
- Hook性能优化
- 资源池化

### 阶段五：文档
- API文档完善

## Impact

### 受影响的能力（新增规范）
- `cpp-architecture`: C++架构设计规范
- `cpp-modules`: 模块化设计规范
- `cpp-memory`: 内存管理规范
- `cpp-performance`: 性能优化规范
- `cpp-security`: 安全编码规范

### 受影响的代码（大规模重写）
- **核心文件**：
  - `tool.cpp` (3543行) → 拆分为10+模块
  - `lua_decrypt_hook.cpp` → 重构为服务层
  - `hook.cpp` → Hook管理器重构
  - `native-lib.cpp` → JNI适配层优化
  - `zip_reader.cpp` → RAII化重构

- **新增文件（预计30+）**：
  - `core/`: 核心基础设施（5-8个文件）
  - `services/`: 业务服务层（8-12个文件）
  - `utils/`: 工具类库（6-10个文件）
  - `jni/`: JNI桥接层（3-5个文件）

### 破坏性变更标记
- **BREAKING**: JNI接口签名可能变化
- **BREAKING**: 全局变量移除，需要通过服务访问
- **BREAKING**: 错误处理机制变更（返回值 → Result<T>）
- **BREAKING**: 部分API命名规范调整

### 风险与收益
**风险**：
- 大规模代码重写，可能引入新bug
- 需要充分测试和验证
- 分阶段实施周期较长（预计4-6周）

**收益**：
- 代码可维护性提升80%+
- 内存安全性大幅提升
- 性能优化预期提升30-50%
- 为未来功能扩展奠定基础
- 降低技术债务

### 迁移计划
采用分阶段、渐进式重构策略：
1. 新代码优先使用新架构
2. 旧代码逐步迁移（保持功能可用）
3. 双轨并行，逐步切换
4. 每阶段完成后进行完整测试
